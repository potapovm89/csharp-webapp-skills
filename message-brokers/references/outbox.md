# Transactional Outbox & Inbox Reference

## Why
A use-case that changes the database **and** publishes a message must not do both directly ("dual write"):
- publish before commit → the message is out, the transaction rolls back → consumers act on data that does not exist;
- publish after commit → the process crashes between commit and publish → the message is lost forever.

The outbox makes the message part of the same database transaction; a separate relay publishes it afterwards. Delivery becomes **at-least-once**, so consumers must be idempotent (see "Inbox" below).

## When It Is Mandatory
- The same use-case writes to the service's database and publishes to Kafka/RabbitMQ — **always use the outbox**.
- Publishing without a DB write (e.g. a pure proxy, a scheduled job that only reads) may publish directly, with producer acks/confirms as described in `kafka.md` / `rabbitmq.md`.
- Never call `ProduceAsync` / `BasicPublishAsync` inside an open DB transaction or right after `CommitAsync` in a handler that also wrote data.

## Outbox Table (migration)
Created through a migration like any other table (see `database-migrations`). It is a **technical table**: no soft delete, physical cleanup is allowed.

```sql
CREATE TABLE outbox_messages (
    id                uuid         PRIMARY KEY,
    broker            int          NOT NULL,          -- 1 = Kafka, 2 = RabbitMQ
    destination       varchar(255) NOT NULL,          -- topic or exchange
    message_key       varchar(255) NULL,              -- Kafka key / routing key
    message_type      varchar(200) NOT NULL,          -- e.g. 'order-created'
    message_version   int          NOT NULL DEFAULT 1,
    payload           jsonb        NOT NULL,
    headers           jsonb        NULL,              -- traceparent, correlation id, ...
    created_date      timestamptz  NOT NULL DEFAULT now(),
    next_attempt_date timestamptz  NOT NULL DEFAULT now(),
    attempts          int          NOT NULL DEFAULT 0,
    last_error        text         NULL,
    processed_date    timestamptz  NULL
);

CREATE INDEX ix_outbox_messages_pending
    ON outbox_messages (next_attempt_date, created_date)
    WHERE processed_date IS NULL;
```

## Writing to the Outbox
- Access goes through a domain service `IOutboxDomainService` in `DataAccess` (EF or Dapper, same as the business tables of that database).
- The insert runs in the **same `ITransactionScope`** as the business change.
- `id` is generated by the writer (`Guid.CreateVersion7()`) and becomes the `message-id` header — consumers deduplicate by it.
- Capture the current trace context into `headers` (`traceparent`, see `kafka.md` "Tracing").
- Keep message creation in one helper (factory) so every outbox row gets the same id, headers and serialization.

```csharp
await using (await transactionScope.BeginAsync(ct))
{
    try
    {
        var orderId = await orderDomainService.CreateAsync(order, ct);

        outboxDomainService.Add(OutboxMessageFactory.Create(
            broker: OutboxBroker.Kafka,
            destination: kafkaOptions.Topic,
            messageKey: orderId.ToString(),
            messageType: "order-created",
            payload: order.ToOrderCreatedDto()));

        await transactionScope.CommitAsync(ct);
    }
    catch
    {
        await transactionScope.RollbackAsync(CancellationToken.None);
        throw;
    }
}
```

## Relay (Publisher)
A relay is an explicit exception to the ban on broker I/O in **business** transactions: this simple implementation holds only outbox row locks while publishing and recording the result. Bound the batch size, each publish timeout and total transaction duration; on broker outage roll back/finish the bounded batch and back off rather than holding locks indefinitely. Do not add business-row updates to this transaction. At higher throughput a claim/lease relay is an alternative, but it needs lease expiry, ownership/fencing and recovery tests before use.

A `BackgroundService` (in the host that owns the database, or in `WorkerHost`) that loops:

1. Open a transaction and lock a batch that other replicas skip:
   ```sql
   SELECT * FROM outbox_messages
    WHERE processed_date IS NULL AND attempts < @MaxAttempts AND next_attempt_date <= now()
   ORDER BY created_date
   LIMIT @BatchSize
   FOR UPDATE SKIP LOCKED;
   ```
2. Pick the publisher by `broker` and publish each message with acks/confirms (`Acks.All` + idempotence for Kafka, publisher confirms for RabbitMQ), copying `id`, `message_type`, `message_version` and `headers` into message headers.
3. On success: `UPDATE ... SET processed_date = now()`.
4. On failure: increment `attempts`, record a sanitized `last_error`, and set `next_attempt_date` to the next bounded exponential-backoff time (e.g. 1s → 5 min). Calculate it in the relay; `backoff(...)` is pseudocode, not a built-in PostgreSQL function. Once `MaxAttempts` is reached, exclude the row from automatic selection, retain it and raise an alert; an explicit operational retry resets its attempts and schedules it again. Never silently drop or endlessly retry an exhausted row.
5. Commit, then wait `PollingInterval` only if the batch was empty.

Rules:
- `FOR UPDATE SKIP LOCKED` makes the relay safe to run on several replicas.
- Run every iteration in its own DI scope and transaction. A transaction scope object must be able to start a new transaction after the previous one was disposed — otherwise the second iteration silently reuses a finished transaction.
- **Per-key ordering**: messages with the same key may be reordered when several replicas relay in parallel or when a failed message is retried later. Strict order requires a deterministic per-key sequence and blocking later messages while an earlier one is pending, including exhausted messages awaiting an operational decision. A single relay alone does not fix reordering caused by skipping a failed message.
- The relay may publish a message twice (crash between publish and `UPDATE`). This is expected: at-least-once.
- Options (`OutboxOptions`): `BatchSize`, `PollingInterval`, `MaxAttempts`, `RetentionPeriod` — registered with `AddOptionsWithValidation`.
- Metrics: `outbox.messages.pending`, `outbox.messages.oldest_pending_age`, `outbox.messages.published`, `outbox.messages.failed` (outcome `retry`/`exhausted`), `outbox.publish.duration` — see `observability`, metrics.md. Alert when the oldest pending message is older than a few minutes or any message is exhausted.
- Manual retry after an outage: through an authorized operational tool, select the intended unprocessed rows, reset `attempts` and set `next_attempt_date = now()`. Log the affected ids; never hand-edit production data or reset rows without an explicit retry decision.

## Cleanup
A Quartz job deletes processed rows older than `RetentionPeriod` in batches (`DELETE ... WHERE id IN (SELECT id ... LIMIT 1000)`). Physical deletion is allowed here: this is a technical table.

## Inbox (Consumer Idempotency)
Every consumer must tolerate duplicates. Use one of the two approaches, inside the **same transaction** as the business effect:

1. **Natural key + unique constraint** — when the message creates an entity with a business key (`store_id + order_id`). Insert and treat a unique violation (`PostgresException.SqlState == "23505"`) as "already processed". A check-then-insert without a unique constraint is **not** enough: two parallel deliveries both pass the check.
2. **Inbox table** — for everything else:
   ```sql
   CREATE TABLE inbox_messages (
       consumer       varchar(200) NOT NULL,
       message_id     uuid         NOT NULL,
       processed_date timestamptz  NOT NULL DEFAULT now(),
       PRIMARY KEY (consumer, message_id)
   );
   ```
   ```sql
   INSERT INTO inbox_messages (consumer, message_id) VALUES (@Consumer, @MessageId)
   ON CONFLICT DO NOTHING;
   ```
   0 rows affected → the message was already processed: commit nothing else, acknowledge and return. Cleanup by retention, like the outbox.

Side effects outside the database (HTTP calls, emails, S3 writes) cannot be part of the transaction. Make them idempotent on the receiving side (idempotency key = `message-id`) or move them behind another outbox.

Inbox/idempotency retention covers the permitted replay and recovery horizon. A DB restore may remove records of messages/effects already executed elsewhere; retain/reconcile external business keys before replay, including pending outbox rows restored to an older state. [data-recovery](../../data-recovery/SKILL.md) owns that drill/runbook; broker producer idempotence alone does not prevent repeated external business effects after a rewind.

## Tests (integration)
- The use-case writes the business row and the outbox row in one transaction; a failure after the outbox add leaves neither.
- The relay publishes a pending row and marks it processed; a broker failure increments attempts and schedules a retry.
- Two relay instances do not publish the same locked row concurrently (SKIP LOCKED); a crash after broker confirmation and before the DB commit can still cause a later duplicate, which the consumer deduplicates.
- A consumer that receives the same `message-id` twice changes state once (inbox).

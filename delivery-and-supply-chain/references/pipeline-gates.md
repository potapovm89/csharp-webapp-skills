# Pipeline Gates

## Stage Contract

Use the existing CI provider. This table defines outcomes, not a portable executable pipeline; translate it into actual job dependencies and validate with that provider's configuration checker. Test a skipped/manual/upstream-failed job as well as the happy path.

| Stage | Required result | Blocks |
|---|---|---|
| Validate source | Protected branch/MR rules, changed-file lint and applicable IaC/config checks | Merge/candidate |
| Restore | Approved package sources and exact resolved dependency graph; no lock-file drift | Build/test |
| Verify code | Full build and applicable unit, architecture, contract, integration and frontend checks (`testing`) | Merge/candidate |
| Security and licenses | SCA with transitive dependencies, secret scan, license caps; applicable SAST/IaC checks | Merge/candidate |
| Package | One image per host from the approved revision and recorded toolchain | Candidate |
| Inspect artifact | Container/package scan, inventory/SBOM of shipped contents, provenance and authenticity evidence | Promotion |
| Verify release | Artifact trust check, migration Job, rollout/functional checks, relevant reliability signals | Next environment |

Required jobs cannot be `allow_failure`, skipped by a changed-path rule that misses shared dependencies, or bypassed by starting a downstream job manually. Documentation-only changes need relevant validation, not Docker builds; shared package/build/CI changes must invalidate affected gates. Separate protected release jobs from untrusted MR jobs, caches and artifacts.

## Repeatable Inputs
- Pin the .NET SDK in `global.json` and local tools in the tool manifest; pin Node/package-manager and security-tool versions where used. Record effective versions and OS/architecture in evidence. Fixing a version still requires a patch/update policy.
- Keep central package versions/transitive pinning (`csharp-code-style`) and commit application `packages.lock.json` files generated by reviewed restore. Use `dotnet restore --locked-mode` in CI. Do not combine locked restore with force evaluation or regenerate locks automatically in a release job.
- Frontend jobs use the repository's committed lock file and the corresponding frozen install (`npm ci` or the pinned package manager's equivalent). Respect the chosen package manager; do not generate a second lock file.
- Use approved NuGet/npm sources and NuGet package-source mapping where needed to prevent private names resolving from a public feed. Cache keys include lock files, toolchain and platform; untrusted jobs cannot poison protected release caches. Hash pinning and caching do not replace source trust checks.
- Restore once for the candidate's chosen target framework/runtime graph; subsequent `dotnet build`, `test` and `publish` use `--no-restore` with matching configuration and inputs. If packaging performs a separate restore (e.g. inside Docker), enforce the same committed locks/sources and record it; tests of a different graph do not qualify the candidate.
- A reproducible-input policy does not prove byte-for-byte reproducible builds. Claim reproducibility only after comparing independent builds and documenting nondeterministic inputs.

## Security Results and Exceptions
- Apply `security` severity rules: high/critical NuGet advisories and high/critical frontend dependency findings block; moderate findings have an owner/remediation decision. Evaluate the shipped image's OS/runtime packages too and define their blocking severities explicitly; absent policy is an unresolved gate, not acceptance. Define applicable SAST/DAST/IaC severity rules in the project policy instead of assigning every finding the same gate.
- A scanner command's exit code may mean only that it ran. Parse its documented result format, record scanner/database timestamps and fail on policy violations. Missing, stale beyond the agreed freshness limit, or unreadable required results are **unknown**, not clean.
- Configure secret scanning for the MR diff and agreed history scope; never publish detected secret values in logs/reports. Rotate a confirmed leaked credential (`configuration-secrets`). Do not upload proprietary source/SBOM to an unapproved external scanner.
- DAST and abuse/load checks run only against approved test environments with bounded scope/data; never point a scanner at production or arbitrary discovered hosts.
- An exception identifies the exact package/advisory or finding, affected digest/version, reason, compensating control, accountable owner, authorized approver, expiry and remediation issue. Scope suppression to that finding; do not suppress the scanner. Expired exceptions block. Do not invent an approval or approve your own bypass.
- Security scans are renewed for a stored candidate before later promotion when evidence is older than the agreed policy. New advisories can invalidate an otherwise unchanged digest.

## Privileged Jobs
- Protected release jobs use least-privilege, short-lived workload/OIDC credentials where supported. Validate issuer, audience and repository/ref/environment claims in the receiving service; masking a variable does not protect it from executing MR code.
- Pin reusable jobs/actions/plugins and build images to reviewed immutable revisions/digests. Protect pipeline/policy/trust-root changes with appropriate review. Never interpolate untrusted branch names, MR text or user input into shell commands.
- Avoid privileged containers/host Docker sockets on shared untrusted runners. Where build infrastructure needs extra privileges, isolate runners and document their trust boundary.
- Secrets are injected per job/environment, not baked into build args, layers, package feeds committed with credentials or cached config. Separate package download, candidate publish, signing and deployment privileges.

## Verification Cases
Test lock drift; a forbidden direct/transitive package; scanner failure/stale database; expired exception; an untrusted MR attempting a protected job; and a changed digest after scans. Each must stop the appropriate stage, with a reason visible without leaking credentials. Keep provider-validation and fixture results with the MR; do not run an actual deployment to prove gate configuration.

Source: [NuGet lock-file and locked-mode behavior](https://learn.microsoft.com/en-us/nuget/consume-packages/package-references-in-project-files), reviewed 2026-11-14.
